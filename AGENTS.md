

Проект

Avito Kitchen — тестовое backend-задание.

Основной сервис реализуется как modular monolith на Go с PostgreSQL.

Demo Cafe — отдельный сервис, взаимодействующий с Avito Kitchen по HTTP.

Цель проекта — простое, объяснимое и надёжное MVP-решение. Не добавляй технологии и абстракции без конкретной необходимости.

Правила работы

* Вноси минимальное связное изменение, необходимое для текущей задачи.
* Не выполняй unrelated refactoring.
* Следуй существующей архитектуре и границам пакетов.
* Не меняй публичный API, модель БД или бизнес-правила без необходимости.
* Не создавай заранее пакеты, интерфейсы и абстракции для будущих задач.
* Предпочитай простое решение, достаточное для MVP.
* Не добавляй зависимости без конкретной причины.
* Не создавай git commit, если это явно не запрошено.



Архитектурные ограничения

Avito Kitchen остаётся modular monolith.

Demo Cafe является независимым сервисом.

Сервисы:

* не импортируют внутренние пакеты друг друга;
* взаимодействуют только через HTTP-контракт.

Не добавляй без отдельного требования:


Kafka
Redis
RabbitMQ
Kubernetes
микросервисное разбиение Avito Kitchen


HTTP handlers отвечают за transport layer и не содержат основную бизнес-логику.

PostgreSQL-specific код не должен определять бизнес-правила.

Внешние HTTP-вызовы нельзя выполнять внутри открытой database transaction.

Заказ должен быть сохранён до начала асинхронной отправки в Cafe Service.

Критичные инварианты

При изменениях обязательно сохраняй инварианты, описанные в docs/design/.

Особенно важно:

* клиент не является источником истины для цены;
* expected_price проверяется против актуальной серверной цены;
* полный menu snapshot применяется атомарно;
* старая версия snapshot не может перезаписать новую;
* повторная отправка той же snapshot version безопасна;
* Order и его OrderItems создаются атомарно;
* OrderItem хранит исторический snapshot названия и цены;
* создание заказа идемпотентно;
* повторная доставка заказа в Cafe Service не должна создавать дубликат;
* business rejection отличается от technical failure;
* состояние, ранее показанное пользователю, повторно проверяется перед созданием заказа.

Если изменение затрагивает один из этих инвариантов, добавь или обнови соответствующие тесты.



Go

Пиши идиоматичный и простой Go.

* Используй gofmt.
* Для I/O операций передавай context.Context первым аргументом.
* Передавай context в PostgreSQL и исходящие HTTP-запросы.
* Не сохраняй context.Context в долгоживущих структурах.
* Оборачивай ошибки полезным контекстом через %w.
* Не сравнивай ошибки по тексту.
* Не используй panic для обычных ошибок приложения.
* Избегай глобального изменяемого состояния.
* Не создавай интерфейс для каждой структуры автоматически.
* Интерфейс должен выражать реальную границу зависимости или помогать тестированию.
* Деньги храни целым числом в минимальных денежных единицах, не float.



База данных

Все изменения схемы выполняются через migrations.

Используй ограничения PostgreSQL для простых инвариантов, когда это возможно:

PRIMARY KEY
FOREIGN KEY
UNIQUE
NOT NULL
CHECK

Не изменяй схему автоматически при запуске приложения.

Не держи database transaction открытой во время сетевого вызова.

Транзакция используется только тогда, когда операция действительно требует атомарности.


API

При изменении публичного API обновляй:


- api/avito-kitchen.openapi.yaml
- api/demo-cafe.openapi.yaml

Используй единый формат ошибок.

Различай:

business conflict


и:

technical failure


Не добавляй endpoint без существующего бизнес-сценария.



Тестирование

Новая или изменённая бизнес-логика должна иметь тесты.

Предпочитай:

* table-driven unit tests для бизнес-правил;
* HTTP tests для handlers и error mapping;
* integration tests для PostgreSQL-specific поведения, транзакций и конкурентных сценариев.

Не создавай mock без необходимости.

Особое внимание уделяй не только happy path, но и сценариям нарушения инвариантов.

Проверка изменений

Для каждого Go module выполняй необходимые команды напрямую.

Avito Kitchen:


cd services/avito-kitchen
go test ./...
golangci-lint run


Demo Cafe:


cd services/demo-cafe
go test ./...
golangci-lint run


Docker Compose:


docker compose config
docker compose up --build
docker compose down


Если конкретный инструмент недоступен в окружении, не скрывай это: явно укажи, какую проверку выполнить не удалось.

Критерии завершения задачи

Перед завершением задачи проверь:

1. реализация соответствует проектной документации;
2. изменение не нарушает архитектурные границы;
3. изменённое поведение покрыто тестами;
4. Go-код отформатирован;
5. тесты проходят;
6. линтер проходит, если доступен;
7. OpenAPI обновлён, если изменился API;
8. добавлена migration, если изменилась БД;
9. документация обновлена, если изменилось принятое решение;
10. в diff нет несвязанных изменений.
